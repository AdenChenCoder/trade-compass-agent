# PWA 页面版本更新

移动端页面与电脑同源分发，不需要额外的版本通知服务。构建时根据页面资源生成版本标识，同时写入 HTML 和 Service Worker。Worker 只有在完整缓存本版页面资源后才能激活；已经打开的旧页面继续使用自己的代码和资源。

## 启动与运行中的行为

| 场景 | 行为 |
| --- | --- |
| 浏览器创建新页面，包括真正关闭后重新打开 | `main.tsx` 在挂载可操作的 App 前调用 `prepareStartupUpdate()`。检查电脑上的 Worker 更新，等待完整安装和激活；版本不同则自动重新加载，再展示 App。 |
| 已打开的页面，或从后台、BFCache 恢复 | 不重新进入启动流程。`AppUpdate` 在回到前台、网络恢复及前台每 60 秒检查更新，显示“检测到新的版本，是否更新？”和“确定”。 |
| 用户点击确定 | 先触发原有 `compass-before-update`，保存当前会话位置和草稿；保存失败则保留页面并提示，成功才重新加载。 |
| 离线、检查超时、新版资源不完整 | 启动等待最多 4 秒，继续使用完整的缓存版本。此后即使检查迟到完成，也只会显示手动确认提示。 |

启动阶段没有可编辑界面，因此不会中断正在输入的操作。运行阶段不自动刷新。启动更新保留原 URL，包括配对 fragment 和通知入口参数；会话、配对、推送凭据、草稿的存储方式不变。

自动重载在 sessionStorage 中记下目标版本，防止异常缓存导致循环刷新；它是临时运行状态，不承载用户数据。已确认的目标版本会清除该标记。无法保存防循环标记时使用手动更新。

这里以“新建文档”和“恢复已有文档”划分，不能依赖退出事件判断手机是否真正杀掉 PWA。移动端关闭事件可能不触发，BFCache 恢复也不等于新建页面。[浏览器生命周期说明](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

## 验证与发布

- `src/startup-update.test.ts` 验证安装完成后才自动更新、4 秒超时、迟到检查、离线、安装失败和防循环。
- `e2e/pwa-upgrade.spec.ts` 使用真实 HTTPS、缓存、Worker 和页面关闭/重开，验证新版在可操作 App 出现前加载、运行中定期提示、恢复事件不刷新、草稿及配对保留、缺失资源和离线回退。
- 现有通知点击、会话创建、详情和同步浏览器用例继续覆盖启动后的产品流程。
- 当前已经打开的旧版本仍执行旧代码，需要先确认一次升级来获得本策略。后续版本才按本策略启动。
- 源码与 wheel 分发同一套资源。更新安装实例前保留原 wheel，保持电脑身份、连接地址和用户数据；纯页面资源更新无需重启服务。

这些测试覆盖浏览器文档生命周期，不替代 iOS/Android 系统任务切换器的真机验收。
