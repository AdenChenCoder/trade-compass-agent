# 手机连接恢复验收

目标是恢复连接后继续原会话，保留手机授权、草稿和通知偏好。入口就绪、推送服务接受请求、手机实际显示通知是不同结果，分别验收。

## 已实现的恢复机制

- PWA 重新打开时，临时 5xx 响应使用已保存的电脑信息继续等待恢复，不要求重新配对。服务明确返回未配对或拒绝授权时，仍按实际响应处理。
- 浏览器请求使用 15 秒超时，避免一次无响应请求一直占住同步。浏览器后台暂停计时的情况仍需真机验证，不能把这个值理解为锁屏期间的严格墙钟上限。
- 手机重新联网、页面恢复显示时触发读取；同一轮同步不重叠。已发送消息的结果仍按原请求编号查询，不在后台自动重发消息。
- 连接组件超过 15 秒未更新状态时，电脑端不再报告入口就绪；新状态恢复后复用原进程、移动监听器和授权。此检查发现的是组件状态过期，不是对所有公网路径进行连通性证明。
- 通知设置恢复读取后清除过期的网络错误，保留其他操作失败提示。

## 自动检查的范围

| 场景 | 验收方法 | 能证明的结果 |
| --- | --- | --- |
| 502 / 503 / 504 后重新打开 | 浏览器请求测试及 React 实际组件渲染，替换网络响应 | 缓存电脑身份保留；恢复后无需刷新即可同步 |
| 请求无响应 | 模拟浏览器 AbortSignal 和时间推进 | 请求结束；原发送请求不会自动重试 |
| 发送后回执丢失 | 组件提交一次消息，恢复后读取原编号回执 | 不重复 POST；确认后清除待确认状态 |
| 恢复期间的草稿和通知提示 | 操作渲染组件，触发 online / pageshow | 草稿保留，联网后清除网络错误 |
| 连接组件暂停 | 暂停隔离子进程，通过本机 API 检查状态后恢复 | 状态不永久停在就绪，原进程和授权复用 |
| 六小时提醒中断 | 推送失败、推进测试时钟、重新打开持久队列 | 原结果不变、任务不重跑、同一提醒编号续发 |
| 已安装包 | 仓库外安装、包目录只读、相关 API 检查与发布冒烟 | 安装包可用，包目录内容未被改写 |

六小时时间推进不是六小时持续运行。React 测试使用 jsdom，不等同于 Safari / Chrome 真机渲染。

实际公网组件暂停恢复已完成：通过正常配对取得临时授权后，暂停并恢复新测试实例的连接子进程；恢复运行后 1.654 秒能用原 Cookie 读取原会话，35 项检查通过。没有暂停整台电脑、切断系统网络或操作手机。安装升级另经本机 HTTPS 验收，不能混记为公网验收。详细记录见[主验收记录](mobile-managed-access-review.md)。

## 已发现但尚未解决的问题

此前两个长期运行的测试入口出现过公网 TLS 握手失败，本地连接状态和组件心跳却正常。仅重启新测试实例后该入口恢复，旧实例当时仍失败；故障开始时间及根因未知。持久化 Funnel 配置没有缺失，不能简单归因于配置丢失。

2026-09-14 随后对旧入口取证：本地证书有效、域名及密钥匹配、本机 TLS 正常，四条公网路径均为 TLS EOF。同一次对照中新入口四条路径均可用。通过原桌面 API 仅关闭、重新开启旧手机入口一次后，55.315 秒恢复四条路径及普通域名的授权读取，36 项验收通过。原地址、两实例历史、身份、既有授权及旧手机通知偏好保留，旧配置字节一致；新入口未重启，临时验收设备已撤销。重开同时加载了新版连接组件，故不能将结果单独归因于重启或代码变化，也不能认定根因已修复。详见[旧入口恢复记录](mobile-managed-access-review.md#手机反馈与旧入口受控恢复2026-09-14)。

状态心跳检查本身不能发现这类故障。此后已补充不含凭据的运行期诊断，以及独立的电脑侧公网 HTTPS 检测，详见[诊断说明](mobile-funnel-diagnostics.md)。检测异常不关闭连接、不触发重新配对；这些能力帮助识别故障，尚未解决其根因，也不能证明长期运行稳定或所有断线均可自动恢复。不得用无条件重启、清空手机授权或降低 TLS 检查来掩盖问题。

## 真机验收

2026-09-14 已补一轮约五分钟的电脑侧连续公网观察：十二轮共 60/60 次路径访问成功，原会话与桌面一致，原授权和进程保持，临时设备已撤销。这是持续有访问的短时结果；同期旧测试入口仍有 TLS EOF，后续恢复见上节。完整范围见[主验收记录](mobile-managed-access-review.md#短时连续公网访问2026-09-14)。

用户随后针对手机短暂断网验收回复“验证了，能够自动恢复”。据此确认这一次手机断网后的自动恢复，不再将此项列为待确认。尚未明确回传恢复耗时、草稿保留、机型、系统或浏览器版本；不能扩展为其他网络、整机睡眠或长期稳定性通过。以下为验收方法与尚未覆盖的路径，不要求用户重复已确认的操作。

先完全关闭旧 PWA，再从主屏幕打开，确认服务更新已生效。保留已有配对。

1. 进入一条原会话，输入一份不发送的草稿。手机开启飞行模式约 10 秒，再恢复网络。记录恢复所用时间；无需刷新或重新配对，原会话和草稿应保留。
2. 在 Wi-Fi 和手机流量之间切换，重复上面的检查。记录实际运营商及网络环境，不把一种网络的成功扩展到其他网络。
3. 手机锁屏后重新打开 PWA，检查当前会话、草稿和任务消息。系统通知的实际出现及点击跳转需要独立确认。
4. 电脑没有正在执行的任务时进行一次真实睡眠 / 唤醒，再检查同一手机入口。电脑睡眠期间不能运行新任务；本轮不修改原调度的恢复策略。

| 此前已连接的手机 | 用户确认过配对、会话、通知及普通重启恢复；本次确认短暂断网后自动恢复 | 手机型号、系统版本、安装形态、恢复耗时、草稿保留及其他网络结果 |
| iPhone / iPad | 官方提供主屏幕 Web App 的 Web Push 能力 | 本项目对应机型、系统、锁屏、网络切换和唤醒验收 |
| 国内 Android | 项目检测浏览器的 Service Worker、PushManager、Notification 能力 | 具体机型、浏览器、推送订阅及实际网络结果 |
| 境外 Android / 网络 | 同一 PWA 和授权协议 | 实际设备、网络及通知到达结果 |

iOS / iPadOS 16.4 起的主屏幕 Web App 可以在用户操作后申请 Web Push 权限；这项平台能力不等同于本项目已完成真机验收。[WebKit 官方说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

浏览器供应商选择系统推送服务，PWA 不能任意替换它。因此连接电脑成功和锁屏通知成功必须分别检查，不能仅按“Android”整体宣布可用。[Chrome 团队的 Web Push 说明](https://web.dev/articles/push-notifications-overview)

## 尚未覆盖的恢复路径

真实整机睡眠、电脑物理断网、长时间网络中断、首次证书准备或真实续期失败，以及供应商撤销授权后的处理仍需进一步验收。当前连接组件因不可恢复错误退出时仍需在电脑点击重试；本轮的手机自动恢复结果不能扩展为所有故障都会自动恢复。

系统通知已显示但向电脑回传接收记录时遇到断网，也不能仅凭桌面端“未回传”推断手机未显示。本轮没有改变这条回传路径。

## 回退

测试实例更新前保留原 wheel。回退只重装该 wheel 并沿用原启动参数，不替换配置、节点身份、手机授权或会话目录。PWA 资源版本会随构建变化；更新和回退后均需重新打开主屏幕应用确认加载版本。
