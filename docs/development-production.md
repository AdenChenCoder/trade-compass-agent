# 开发与稳定运行

源码目录用于开发和隔离验证。本机长期运行的投资服务使用经过审查、推送远程、正式发布并验收的 Python 包。源码与安装包保留相同的产品操作路径，但开发中的版本不会自动进入稳定服务。

## 环境边界

| 项目 | 开发与验证 | 稳定服务 |
| --- | --- | --- |
| 程序 | 源码或本地候选 wheel | 从正式发布渠道安装的固定版本 |
| 配置 | 独立测试配置，禁用自动投资和真实投递 | 用户实际配置，位于源码之外 |
| 数据和记忆 | 独立可写根目录 | 持久化生产根目录，禁止测试写入 |
| 端口和进程 | 独立端口和测试进程 | 既有受监督服务，唯一写入者 |
| 发布凭证与账号 | 模拟响应或明确限定的集成验证 | 原有凭证、授权和设备身份 |

使用 `TRADE_COMPASS_CONFIG`、`TRADE_COMPASS_ENV_FILE`、
`TRADE_COMPASS_DATA_DIR`、`TRADE_COMPASS_MEMORY_DIR` 显式指定验证根目录。
仅设置 `TRADE_COMPASS_HOME` 不足以隔离源码运行：源码仍可能读取仓库配置和 `.env`。
单元测试须显式模拟模型执行；清空 API key 不能禁用本地模型服务。

源码服务尚未迁移时，它仍可能延迟导入修改后的文件。此阶段在隔离副本中执行审查和构建，不在正在提供服务的目录中更新实现、重建前端或重启服务。保留旧服务直到正式包验收完成，再进行切换。

### 长期运行的源码 UI 预览

源码预览通过 `TRADE_COMPASS_WEB_DIST_OVERRIDE` 指向 `temp/web-preview`，使用 `pnpm --dir apps/web build:preview` 更新。不要一边提供发布目录 `web_dist`，一边对它执行清理构建：已打开页面仍可能请求旧的懒加载资源。

验证从更新前已打开的页面继续导航，以及冷启动页面；不得自动刷新草稿或活跃对话。核对源码、构建产物、服务进程、浏览器缓存和 service worker 实际加载的版本。修改服务代码后，通过既有监督器重启并验证新进程与受影响的任务入口，不能将新导入的处理器与旧缓存模块混合当作升级完成。

## 提交和发布验收

1. 按完整功能划分改动，检查依赖闭包。未完成、未验收或存在阻断缺陷的功能留在开发区；使用明确的文件清单准备提交，排除本机配置备份、工作树、运行数据及 `temp/`。
2. 从待提交的确切内容运行相关测试、前端检查与构建、资产检查和 `scripts/ci_check.sh`。独立提交还应在基线加该提交的环境验证，避免依赖未提交文件。
3. 构建 wheel 和 sdist，运行 `scripts/check_dist.py`。在仓库之外创建环境，安装候选 wheel，核对导入路径，运行 `python -m trade_compass_agent.release_smoke`；验证首次配置、CLI、API、前端资产、失败恢复，以及涉及的重启和升级路径。
4. 审查通过后提交并推送远程，使用与包版本一致的正式标签触发现有发布流程。远程 CI、制品检查、发布后的重新安装验收均须通过；上传成功不能代替验收。
5. 再从正式发布渠道安装该确切版本，在独立可写目录重复关键用户路径。记录版本、提交、制品摘要、测试环境和实际结果。需要外部授权或真实设备的能力必须单独记录实测结果；模拟不能证明实际授权或公网连通。

正式包可以通过项目现有的 `uv tool` 安装方式部署，并将版本固定为已验收的版本，例如包规格 `trade-compass-agent==X.Y.Z`。需要可选依赖时保留实际使用的 extras。不要用 editable 安装、本地候选包或源码路径替换稳定服务。

构建与发布工具须支持构建后端生成的元数据。上传前用发布流程所使用的 Twine 版本校验 wheel 和 sdist；TestPyPI 与正式发布流程使用相同、经过审查的发布 action 修订。

### 模型报告的发布前验收

涉及报告校验、修复或降级时，先保存失败运行的业务任务、日期与时区、原始工具回执、模型配置、结构化草稿和校验结果。事故原件保留在隔离的调查目录；进入仓库的回归样本须去除凭证和私人数据，并保留复现所需的语义。只保存最终错误文案或 Agent 摘要不足以复现问题。

在切换稳定服务前，完成两层验证：用固定输入重放失败结构以证明确定性修复，再用实际配置的模型、冻结回执和隔离根目录，通过受影响的真实任务入口生成并审核报告。对于定时任务，应覆盖调度包装、执行、报告发布和持久化后的 API 读取；直接调用校验器不能代替这条路径。预先固定场景、调用预算和通过标准，保留每次失败，不得反复采样直到偶然成功后只报告最后一次。

至少验证以下适用场景，并核对正文、证据、执行结果、报告完整度和用户可见状态的一致性：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 证据充分的事实与合法派生判断 | 正常完成；判断引用经过验证的计算时仍能追溯原始事实，条目换序不改变结果 |
| 真实资料缺口或尚无依据的结论 | 保留已核实内容和具体缺口；不能因为减少误报而放行，也不能把正常执行误报为执行失败 |
| 无效引用、范围或单位冲突 | 仍被拒绝；模型同意不能清除确定性冲突 |
| 修复、超时和取消 | 有界终止并保留真实状态；工具调用记录证明修复没有重放交易、学习或投递等副作用 |

固定回执验证不证明实时数据可用，模拟模型也不证明真实模型会生成有效结构。正式包的隔离验收通过后，切换只使用已授权且范围受限的生产验证，保持交易与其他写操作隔离；自然调度尚未观察时明确记录该范围，不补跑投资任务。

## 首次切换

切换前记录现有解释器和 CLI 路径、服务定义、工作目录、配置和环境文件、数据和记忆路径、监听地址，以及手机访问身份和授权的存储位置。不要只根据端口或进程名称判断运行版本。

准备好已验收的正式包、目标路径、迁移清单和恢复方案后，安排短暂切换窗口：

1. 停止新任务并等待已开始的写入结束，停止原监督服务；确认没有遗留写入进程。此时制作一致性备份，覆盖数据库、文件账本、配置、记忆、会话、调度状态及设备身份，限制备份权限。
2. 把持久化状态迁移到源码之外，保留原路径的恢复副本。校验数量、内容、权限和所有绝对路径引用；不要通过重新初始化账号、重新配对或删除历史解决迁移错误。
3. 用已安装正式包的入口生成或更新原监督服务。保留监听地址和既有监督机制，移除指向开发源码的可执行文件、工作目录、`PYTHONPATH` 和资源路径。
4. 只启动一个写入生产根目录的实例。核对实际 PID、包版本、导入位置、配置、数据路径和浏览器加载的资源。验证现有账户、余额、成交、会话、记忆、定时任务和手机访问均保留。
5. 验收包括冷启动和已有页面刷新/更新、重启后历史可访问、草稿及设备授权保留。禁止补跑错过的自主投资任务作为验证。

## 升级与恢复

升级沿用相同发布与验收流程。保留前一正式版本、服务定义和一致性备份；先确认旧版本能读取升级后的状态，再决定是否只回退程序。涉及不兼容数据变化时，停止写入、预览恢复范围并恢复匹配的备份。恢复不能与运行中的写入并行，也不能丢弃升级后新增记录而不说明影响。

回滚兼容性检查必须包含新版运行后新增的记录和会话正文，并通过旧版的正常读取入口验证用户仍可访问。仅验证旧备份可恢复或数据库能打开，不足以证明程序回滚安全。验收失败时保留失败记录；数据兼容的情况下优先回退程序并保留当前数据，恢复旧备份须单独评估新增数据的影响。

只有正式包和生产切换都通过验收，才能把该版本标为本机稳定版本。开发测试通过、构建成功或远程发布成功分别记录，不能代替这一结论。
