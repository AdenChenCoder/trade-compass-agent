# 统一静态 PWA 与电脑直连验证

用户已允许统一 HTTPS 静态页面分发。目标是手机安装页面、继续电脑上的同一个会话、查看任务消息，同时保留“没有业务云中心”的边界。此次为**同一网络直连验证版**，不是已完成外网自动连接和全平台通知的正式发行版。

## 为什么改变连接方式

统一站点的页面不能直接使用电脑自签名 HTTPS 服务的同源 Cookie。采用 WebRTC DataChannel，由浏览器与电脑协商 DTLS 加密；电脑本地界面生成包含证书指纹的 offer，手机生成 answer，再由用户在电脑导入。交换信息必须来自用户自己的两台设备，不能导入不明来源的信息。

参考 [aiortc API](https://aiortc.readthedocs.io/en/latest/api.html) 和 [WebRTC 连接说明](https://webrtc.org/getting-started/peer-connections)。这里只复用它们的数据通道机制：本项目的授权设备仍对应 `DeviceStore`，会话对应原 `SessionStore`，发送对应 `MobileTurns` 的持久请求回执。参考库不决定本项目的权限、历史或任务语义。

两端均显式设置 `iceServers: []`，没有使用库默认公共 STUN。人工交换连接描述代替信令服务。不是所有 Wi-Fi 都允许设备互访；跨网络、NAT 穿透以及手机后台挂起后的自动重连均未实现。电脑正在睡眠或 Agent 服务未运行时，不能执行新请求。

## 已修正的产品交付方向

用户已明确拒绝使用 GPT / Sites 的页面上传和托管能力作为移动端交付方式，并进一步确认主要问题是交付归属，要求项目自带移动端入口。因此，之前的 Sites 测试页不再作为项目入口，不继续发布或扩大其访问范围。移动端随项目源码和 Python wheel 分发，通过项目的 `/mobile/` 入口提供；电脑“设置 → 连接手机”包含“打开移动端界面”链接。不因这次交付修正擅自重做页面，也不换一家托管平台继续发布。

历史测试站点当前仍仅创建者账号可访问；现有工具没有下线接口，尚未删除。该记录用于说明已有外部状态，不代表继续采用这一方案。源码和运行代码中没有绑定这个站点域名，没有 Sites 登录或运行 SDK 依赖。

下文人工交换连接信息的步骤仅保留为已验证的技术原型，不是用户认可的产品安装流程。

## 项目自带入口

启动当前版本电脑 Web 服务后，在“设置 → 连接手机”点击“打开移动端界面”，或访问同一地址下的 `/mobile/`，例如默认本机服务的 `http://127.0.0.1:19704/mobile/`。开发 Web 的 `/mobile/` 请求也代理到同一电脑服务。

此页面直接读取包内 `mobile_dist` 资源；打开页面不会自动开启手机访问，不生成新的设备授权，也不会启用第二个任务调度器。入口在手机访问开关关闭时仍可预览，实际连接需要用户开启并批准。原有 `/phone/` 同源 HTTPS 兼容入口保留。

本机 HTTP 预览不等于手机 PWA 已经可安装：手机上的 localhost 指手机自身，不能用于访问电脑。手机真实安装仍需可信 HTTPS 与可达网络路径；这项部署条件尚未通过项目提供自动配置，不能用 GPT 托管页代替产品实现。

## 技术原型验证步骤

1. 构建项目界面：`pnpm --dir apps/web build`、`pnpm --dir apps/mobile build`。正常 Python wheel 已包含电脑和移动端资源，以及 `aiortc` 依赖。
2. 通过项目 `/mobile/` 入口本机验证；手机测试需要为项目移动端资源提供可达的可信 HTTPS。当前不上传到任何页面托管平台，也不开放整个电脑管理 API。
3. iPhone 在 Safari 打开网页，选择“分享 → 添加到主屏幕”，从桌面图标打开。Android 使用支持 PWA 的浏览器安装或添加到桌面。
4. 电脑“设置 → 连接手机”开启连接，在“PWA 直连验证”中点击“生成直连信息”。可填写静态网页地址生成扫码链接；信息较长不能生成二维码时，使用复制方式。
5. 手机粘贴“电脑直连信息”，点击“生成手机返回信息”。将返回信息复制到电脑，点击“建立直连”。这些信息 5 分钟内有效，不上传至静态站点。
6. 回手机点击“电脑已导入，继续连接”。首次配对核对两端六位数字，在电脑批准。随后手机读取原会话、发送消息、查看应用内任务消息。
7. 刷新页面、断开或电脑服务重启后，重新交换连接信息。批准记录和手机草稿保留；不会自动重发消息或重复批准。连接不可恢复时，电脑可撤销设备、手机可清除本地连接再配对。

二维码长度限制和两端复制步骤是目前明确的体验缺口。该验证不应被包装成面向普通用户的一键配对完成版。

## 数据、授权和生命周期

- 电脑只有一个 Agent 会话源、请求回执源和任务通知源。DataChannel 请求通过固定白名单进入同一个手机 ASGI 应用，不提供通用 HTTP 代理，不开放电脑管理 API。
- 初次配对仍需电脑批准。DTLS 连接成功本身不授予会话读取或发送权限。
- 统一静态 PWA 使用浏览器本地的随机设备凭据，电脑只存其哈希；与同源模式的 HttpOnly Cookie 区分保存。网页来源、分发账号和更新供应链必须可信，因为同源网页代码可以访问浏览器保存的凭据和缓存。
- offer/answer 保存在两端当前页面。静态页面 URL 的配对信息放在 fragment，页面读取后清除地址中的 fragment，不作为 HTTP 查询发送。
- 电脑服务关闭手机功能时关闭 TLS 和 RTC 连接；不建立第二个 scheduler。撤销设备时关闭匹配的 RTC 连接，并删除该设备推送订阅。已接受的 Agent 任务不因手机切换页面、网络断开而停止。
- 最多 4 条连接，每条最多 8 个并发请求；请求最大 64 KiB。历史响应分段传送，超过 8 MiB 提示在电脑查看。未完成授权的通道有时限。
- 手机原有历史缓存、草稿和请求 ID 仍保留。清除手机本地连接不删除电脑原始会话；离线移除无法通知电脑撤销，需在电脑设备列表补做撤销。

## 通知

浏览器申请系统通知订阅，电脑保存订阅并通过 Apple/FCM/Mozilla 的 Web Push 服务发送**测试通知**。静态站点不转发推送。电脑 VAPID 联系 URI 在没有电脑 HTTPS 地址时使用固定项目主页，签名密钥仍仅存电脑。

统一静态 PWA 的 Worker 无法在手机后台建立新的 RTC 通道，因此显示通知后仅在本机 IndexedDB 保存测试回执 ID；重新直连并打开“连接”页后回传电脑。该派生队列最多 100 条，不是业务消息记录。任务消息仍从电脑原通知记录读取；定时任务自动系统推送尚未接入。

iOS 的主屏幕 Web Push 能力不代表所有 Android 浏览器具备相同能力；尤其不能承诺国内 Android 的 Google 推送网络可达。见 [WebKit 官方说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)。真机安装、真实 APNs/FCM、锁屏显示和国内网络兼容性均需验证。
